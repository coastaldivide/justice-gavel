# Hand-off: account security and the second sandbox review (November 17, 2026)

Branch **`ui-cleanup-2026-11-13`** (PR #4), on top of `sandbox-fixes-2026-11-12` (PR #3). On November 17 the app was run again in a sandbox, front end and back end, and a second, independent agent was asked to find what the first pass missed. It reported 10 issues. I reproduced every one before fixing it. Two more items came from my own report that day.

Every fix below has a test that runs the attack (or the bug) against the real app and real Postgres and shows it no longer works. The same test shows the normal use still works. Migration **051** must be applied before this backend starts (`backend/scripts/migrate.sh` does it on deploy).

## The 10 findings

| # | Finding (reproduced) | Fix |
|---|---|---|
| 1 | **Anyone could join a firm by its invited address.** An invitation was accepted by any signed-in account whose e-mail matched, but e-mail addresses are never proven. A stranger could sign up with the invited address (or, before fix 2, change their e-mail to it) and join the firm in that role. In the sandbox, the agent made "Bob" a partner in firm 1 this way. | Joining now needs the **invitation token**, e-mailed to the invited address as `…/firm/join/<token>`, **and** an account signed in with that address. Only a SHA-256 of the token is stored; migration 051 hashes any old tokens. New: `GET /api/firm-acquisition/invite/:token` and `POST /api/firm-acquisition/invite/accept { token }`. The new app page `FirmJoinScreen` is the link target. `GET /invites` now always returns `[]`, and `POST /invites/:id/accept` needs the token. Both are kept for older app versions. Without an e-mail provider, nothing is sent and the admin gets the link to pass on themselves (the screen shows it). |
| 2 | **A stolen session could take over the account.** `update-profile` changed the e-mail and phone with nothing but a session. A thief could move the account to their own address and then reset the password. | A **new e-mail** needs the current password (400 `password_required`, 403 `incorrect_password`). It is stored as pending and used only after the link sent to the new address is opened (`POST /api/auth/confirm-email { token }`, 24 h, single use, hash stored). The old address is told, with the new one partly hidden. Confirming ends every session and voids open reset links. A password reset or change cancels a pending change. A **phone number** can no longer be set here (400 `phone_needs_verification`); it changes only through the texted-code flow. New app page: `ConfirmEmailScreen` (`/confirm-email?token=…`). |
| 3 | **Old tokens kept working after a password change.** The access token (30 days) still worked on `/auth/me` and could be exchanged on `/auth/refresh`. | Each account has a **session version** (`users.token_version`), and every access and refresh token carries it (`tv`; SSO tokens too). The following add one to it and end every older token at once with 401 `session_revoked`: a password change, a reset, a confirmed new e-mail, `logout { allDevices: true }`, and a replayed (already rotated) refresh token. Both refresh paths check the version. Two more changes came from testing this. A device that was signed out (its refresh token deleted) and then tries to refresh is simply refused; before, that counted as "theft" and also signed out the session that made the change. A plain logout now deletes its refresh token instead of marking it used. Tokens from before 051 carry no `tv` and count as 0, so nobody is signed out by the deploy. The service runs one instance (`render.yaml`). With more instances, another instance notices within the 60 s principal cache. |
| 4 | **One wrong password re-locked an account forever; phone accounts could not reset.** The per-account failure count never went down. Once it reached 50, every single failure after a lock locked the account again. Accounts made with a phone number had no reset at all. | The count is now a **rolling 15-minute window** (`failed_login_window_start`) and starts again from zero after a lock. **Forgot password works with a phone number:** the link goes by text message. Telnyx not set up gives 503 `sms_unavailable` for every number. Numbers that replied STOP get nothing. The answer is the same `{ sent: true }` whether or not an account uses the number. At most 3 links an hour and one a minute per account. On the sign-in screen, "Forgot password?" accepts either. |
| 5 | **Two accounts could share a phone number.** | Unique indexes on `phone`, `LOWER(login_identifier)` and `LOWER(email)` (migration 051). If a database already has duplicates, the migration **stops and lists the account ids**; it never merges or edits accounts (see below). The phone flow refuses a number another account signs in with (409 `phone_in_use`, before any text is sent). A number another account only keeps as a contact moves to the account that proved it, because numbers get recycled. Sign-up checks e-mail, phone and sign-in identifier together. |
| 6 | **The free AI limit could be bypassed.** "3 per day" meant the day in whatever time zone the app sent (`X-Timezone`), so changing the header gave 3 more. It was also checked before answering and counted after, so questions sent at the same moment all passed. Deleting chat history reset it too. | **3 per rolling 24 hours, whatever the time zone.** A question takes a row in the new `chat_quota_log` before it is answered. One reservation at a time per account (row lock), so 6 parallel questions give exactly 3 answers. A question that got no answer is refunded: the model call failed or was refused, or a stream stopped before anything was shown. History is separate, so deleting it gives nothing back. The 402 `resets_at` is when the next question is free, and the app shows that time. On deploy, questions from the last 24 h are copied into the log. |
| 7 | **Court-day messages ignored the hearing time.** A 07:00 hearing got its "court today" reminder at 06:30. A 16:30 hearing was asked "Did you make it?" at 15:00, before it started. | "Court today" goes at 06:30, or **2 hours before** a hearing that starts before 08:30. "Did you make it?" goes at 15:00, or **2 hours after** a hearing that starts after 13:00. A hearing added on the day after it already started gets no "now" message. This applies to the app's reminders, followers, Bond Desk and public defender texts (shared `dayOfReminderAt` / `attendanceAskAt`), and to the guest plan on the phone (it was 1 hour before; now 2, the same as the server). **For counsel (§3.3 of `docs/COUNSEL_REVIEW_PACKET.md`, updated):** a 07:00 hearing now gets a text at 05:00. If a state's quiet-hours rule forbids that, change `DAY_OF_LEAD_MINUTES`. |
| 8 | **The Terms screen was cut off on small phones.** At 320×568 the pinned checkboxes and button left almost no room for the summary, and the button could fall off-screen. | When pinning them would leave less than 200 px for the summary (small phone, large text, long translation), they **scroll with the summary** instead. "Read to the end" now means the summary's last element has been on screen. The button label wraps. Checked at 320×568, 360×640, 390×844, 768×1024, 1280×900 and 1440×900. |
| 9 | **Password edge cases.** bcrypt ignores everything after 72 bytes, so two long passwords that start alike were the same password. The new password could equal the old one. A change did not void reset links already e-mailed. A wrong current password answered 401, which signs the app out. | At most **72 bytes** (400 `auth.err.password_long`, which explains that accented letters count as 2 to 4). The new password must differ (400 `password_same`). A change voids open reset links. A wrong current password is 403 `incorrect_password`. |
| 10 | **Web titles and paths.** The browser tab on Home read "MoreHome". The My rights / Get help / Court dates tabs had one bare path each, so a screen opened inside them had no URL, and reload or Back lost it. | Every tab title is "<screen> · Justice Gavel", or "Justice Gavel" when a screen has no title; never a route name. The three tabs get the same treatment as Home: `/my-rights/…`, `/get-help/…`, `/my-court-dates/…`. The shared paths (`/court-dates/5`, used in texts) are unchanged. |

## Found by the independent re-check (and fixed)

After these fixes, a second, independent agent tried to break each one against its own copy of the API. It confirmed 1 and 3–10 as fixed. On **2** it found one more way in:

- **`PUT /api/court-dates/preferences` also wrote `users.phone`**, with no proof of the number. A stolen session could put its own number on the account, then reset the password by text and take the account over. The agent did exactly that end to end. **Fixed:** this route no longer sets a number. A `phone` that is not the account's current number gets 400 `phone_needs_verification`; turning texts on without a number gets 400 `need_phone`. The app's court-date page now shows **"Add your mobile number"**, which opens the texted-code screen, instead of a free-text field, and refreshes when the person comes back. A test replays the agent's attack: the reset text never reaches the attacker's number. I then searched every SQL statement in the backend for a write to `phone`, `email`, `login_identifier` or `password_hash`. The only writers left are the guarded ones above.
- On a second pass (after the fix above, which it confirmed, along with a scan finding no other unguarded writer of phone, e-mail, sign-in identifier or password), it pointed out that **`routes/firms.js` had two more invite routes** that 051 had left behind. `POST /api/firms/:id/members/invite` stored the token raw and handed it to the admin. The app's link page looks tokens up by hash, so it could not accept these, and the migration had hashed older raw tokens, so `accept-invite` could no longer match those. `POST /api/firms/:id/invite` e-mailed a "firm code" that no route accepts, and its invitations had no token at all. **Fixed:** all three firm-invite routes now share one helper (`createFirmInvite`: hashed token, the e-mailed `/firm/join/<token>` link, the token handed to the admin only when nothing could be e-mailed). `POST /api/firms/accept-invite` now uses the same checks as the app's accept: hashed lookup, the invited address in any letter case, seats, and one use only. These routes still allow membership in several firms, as before. Tested in `account_security.int.test.js`.
- From its notes, also done: **Settings → "Sign out on all devices"** (`logout { allDevices: true }`). Without it, the app had no button that uses fix 3. A plain sign-out ends only this device's refresh token. Its 30-day access token stops being renewed but is not revoked; "Sign out on all devices" or a password change revokes it.
- Noted, not changed: the invitation page shows the invited address to whoever opens a valid link. That link only reaches the invited inbox, and the page needs the address to tell the person which account to use.

## Duplicate accounts (only if migration 051 stops)

If the migration stops, the error message lists the account ids, for example `Same phone: [number ending 0100: accounts 12, 57]`. It prints only the last 4 digits. To see the rows:

```sql
SELECT id, email, phone, login_identifier, created_at, last_seen FROM users
 WHERE phone IN (SELECT phone FROM users WHERE phone IS NOT NULL GROUP BY phone HAVING COUNT(*) > 1)
 ORDER BY phone, id;
-- same for LOWER(login_identifier) and LOWER(email)
```

For each group, decide which account keeps the number or address. Usually that is the one that signs in with it, or the most recently active one. Clear it on the others with `UPDATE users SET phone = NULL WHERE id = …`; they keep their own e-mail sign-in. Then run the migration again. **Never delete an account to resolve this.** People's cases and court dates hang off it. Production data has not been checked from here.

- `backend/src/__tests__/integration/account_security.int.test.js`: 26 tests on real Postgres with local Resend and Telnyx stand-ins. They cover each finding above and the migration's duplicate guard (run in a rolled-back transaction).
- `backend/src/__tests__/court_reminder_times.test.js`: reminder and check-in times in 4 time zones, and the byte rule for passwords.
- `frontend/src/__tests__/render/accountSecurity.test.tsx`: the firm-join and confirm-email pages, forgot password by text, the limit message, the Terms screen at 320×568 and 390×844, and tab titles. `webPaths.test.tsx` covers the tab paths.
- `corePath.test.tsx` and `coreStates.test.tsx`: the court-date page's "Add your mobile number" button (no number field) and "Sign out on all devices".
- Some older tests asserted the old behaviour. Each was changed to assert the new one, with a comment saying why; none was deleted or skipped. They were: the e-mail-matched invite list, the 401 on a wrong current password, phone changes through `update-profile` and the court-date settings (those tests now put the number on the account the way the verify flow does), phone reset as a 400, the source scans of `ctx.limited` and `updates.join`, and the route counts. The route sweep now runs the routes that can end sessions (logout) last, one at a time, then signs everyone in again. Since 051, ending sessions ends access tokens too, so a parallel route would otherwise see a 401 it did not cause. Logout's `allDevices` must also now be exactly `true`.
